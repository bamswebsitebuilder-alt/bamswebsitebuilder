# BAM client service agreement workflow

Implemented against repository `bamswebsitebuilder-alt/bamswebsitebuilder`, starting at `04611b7`, on branch `client-service-agreements`. The agreement workflow and Firebase rules were deployed after the owner's authorization, followed by matching portal icons. The Jotform API update adds administrator-only submission review. No real agreement was submitted or marked signed during development.

## Operating the workflow

1. Sign in as an existing administrator and open **Client Agreements**. The original Projects → Client quotes and agreements workflow remains separate and continues to govern existing quote acceptance/payment dependencies.
2. Choose a client, edit the recovered 18-section agreement, complete client/project/payment/date placeholders and supply the exact statement of work. Signature placeholders remain for Jotform. Review and assign the fixed record. Assignment does not sign anything or collect payment.
3. The verified client sees it under **My Agreements** in the existing Agreements panel. Both English and Spanish routes include the new section; the new agreement content and controls currently use English so the legal draft is not silently translated.
4. A client-specific Jotform invitation overrides the configured default. Otherwise the default is `https://form.jotform.com/263058308288060`, supplied by the owner. Pending agreements automatically show the signing form inside **My Agreements**. Clients have no external Jotform signing link or extra preview button. The contained frame permits forms, scripts and downloads but blocks parent-page navigation and popups. Jotform's current `activeRedirect: thanktext` setting keeps confirmation inside the form. Staff retain an external review link and optional preview. The authenticated API inspection confirmed an enabled LEGACY form with the 18 agreement sections and client/provider signature fields; required-field settings are managed in Jotform. This remains distinct from a verified two-recipient Sign workflow.
5. Under an assigned agreement, staff can enter its Jotform submission ID and select **Check Jotform submission**. The server authenticates the administrator through Firestore, verifies the configured form and the assigned client's email, and reports which signature fields contain values. It does not send signature images or the key to the browser. The lookup fills a reference but never changes signing status. Staff then review signer identities and the exact agreement text in Jotform before recording **client signed**, **both parties signed**, or **cancelled**. A reference/reason and explicit staff review are required. Completion also requires a PDF beginning with `%PDF-`, no larger than 700 KiB.
6. The completed PDF becomes available to the assigned verified client and administrators. Completed/cancelled records and uploaded PDFs are immutable through the application rules. Assign a new agreement for amendments; old agreements remain accessible.

## Security and data

New records live at `users/{uid}/serviceAgreements/{id}`. Assignment text, client, version, link and creation metadata cannot be changed after issue. Clients cannot change signing status, issue agreements or upload completion evidence. Status transitions and PDF creation must commit atomically. The signed PDF is a separate byte record at `documents/signed`, fetched only when the authorized user requests it. No public Storage token URL is created. The existing Storage rules/files are untouched. The 700 KiB limit keeps the PDF within Firestore document limits; compress larger PDFs before upload. PDFs are not included in agreement-list snapshots, local/session storage or the service worker's static caches.

Strict field/type/size validators and timestamp checks apply to new agreement records. Existing project/quote rules were preserved. Emulator tests cover unauthenticated/cross-client/unverified access, role escalation, missing/extra/oversized/malformed data, immutable terms and ownership, invalid status transitions, completion without a PDF, non-atomic uploads, oversized PDFs, orphan documents and mutation/deletion of retained copies. These checks do not verify the actual legal contents of a PDF or replace staff signature review.

Notifications: assignments/status updates appear in live agreement cards, inline change notices and the admin Notifications activity list. Existing browser notification permission enables alerts while the page is open. No background push, email, scheduled reminders or Jotform webhook is installed. Admin activity currently reflects the most recent status per agreement; this is not a full event/audit log. Jotform's signature audit trail should accompany the completed document.

## Jotform setup still needed

- Confirm the provided form contains the finalized agreement and statement of work and has the correct client and BAM representative signature/date fields, electronic records consent and separate portfolio choice. Configure a true two-recipient Sign workflow if that is required; an ordinary public form embed does not establish that workflow.
- Use recipient-specific invitations per assignment for client identity and routing. Do not put client-specific invitation links or secrets in the public configuration file. Staff must check signer identity and the agreement text before recording completion.
- Production now has a server-only `JOTFORM_API_KEY` stored as a sensitive Vercel variable and `JOTFORM_FORM_ID` identifying this form. The key was verified by read-only calls to Jotform. The `/api/jotform-agreements` endpoint allows only authenticated administrators to check the connection or review a matching submission. It forwards the administrator's original Firebase ID token to Firestore, where Firebase verifies it and applies the existing rules. Decoded token data selects a profile path only and is never accepted as proof of identity. No production Firebase service-account credential or additional Firestore permission is required.
- To automate final signing status and PDF retrieval, first configure and verify a true recipient-based Sign workflow, authoritative completion data, an exact assignment-to-document mapping, and secure callbacks. Ordinary signature-field presence is insufficient to verify separate signers or the exact assigned agreement. Never trust an iframe success message or an unverified callback to mark an agreement signed. No webhook is installed. Do not paste the key into `js/service-agreement-config.js`, source files or the browser.

## Configuration and release

`js/service-agreement-config.js` contains public defaults only: the owner-supplied form link and `displayMode: 'embed'`. The display mode controls the optional staff preview; client signing always stays embedded. Each assignment stores its own link snapshot; later default changes do not alter existing assignments. Do not configure Jotform to redirect the entire parent page after submission.

The existing `bam-client-portal` default database was confirmed as STANDARD / FIRESTORE_NATIVE. The additive agreement rules were deployed first and verified against the tested source; website releases use the existing Vercel Git integration on `main`. The API review update requires a fresh production deployment after setting its two Vercel variables, and changes no Firebase rules, profile data, agreement status or Storage configuration.

Validation performed: 29 model/portal/API/quote automation tests; 50 agreement Firestore security checks and 35 existing quote security checks from the rules release; browser interaction checks on both admin routes and the client section using isolated Firebase/API doubles, including read-only submission lookup. No live Jotform signing, real client account test or production PDF transfer was performed. A live authenticated Jotform API inspection confirmed the key and current form; real administrator submission lookups require an actual signed-in administrator session and a submitted form.
